## 🚀 5 分钟看懂这个项目（大白话版）

### 0.1 一句话

**把网盘（阿里云盘/夸克/115/百度）里的音乐和有声书，直接当成本地媒体库来用，
而且播放时音频数据不经过你的 NAS。**

### 0.2 为什么要绕这么大弯

如果直接把网盘挂载成本地目录来扫：扫描会把每个文件**从头到尾读一遍**（读标签、算哈希），
几万首歌 = 几 TB 流量 = 网盘风控直接把账号干掉。

所以这里用**“只索引、不搬运”**：

```text
① 把网盘文件夹加成媒体库（路径写成  openlist://192.168.1.10:5244/fnos/音乐 ）
   ↓
② 扫描器只问 OpenList 一句：“这目录下有什么？”
   → 一次纯 JSON 调用，拿到 文件名/大小/修改时间，不下载任何文件内容
   ↓
③ 从 目录名/文件名 解析出 艺人-专辑-曲目，写进 SQLite（= 建库）
   需要真实标签（时长/码率）时，才对直链发 HTTP Range 只取 头 2MB + 尾 2MB
   ↓
④ APP 播放时，服务端去要一个“网盘直链”（有时效的签名 URL），
   回给 APP 一个 302 跳转
   ↓
⑤ APP 直接从网盘 CDN 拉音频 —— 音频数据完全不经过你的 NAS
```

### 0.3 OpenList 是什么

一个自部署的网盘网关（AList 社区续作，https://github.com/OpenListTeam/OpenList）。
它把夸克/115/百度/阿里统一成一套 HTTP API，**并且能吐出直链**。
我们不自己写网盘爬虫（会被封），全部通过它对接。

部署：见 **§6**。你要知道的只是它的地址（如 `http://192.168.1.10:5244`）。

### 0.4 三条兑底链路（播放失败时会自动降级，用户无感知）

| 优先级 | 链路 | 什么时候走 | 媒体数据过 NAS 吗 |
|---|---|---|---|
| 1 | **302 直链** | 默认 | ❌ 不过，APP 直接从网盘 CDN 拉 |
| 2 | **中转流** | 直链过期 / 绑定请求 IP 拉不动 / 被配置关闭 | ✅ 过，服务端当二传手 |
| 3 | **转码流** | 客户端要低码率（外网听无损） | ❌ 不过，ffmpeg 自己从直链拉流再转码 |

### 0.5 两个媒体类型都要支持

**音乐**（`mediaType = "music"`）和 **有声书**（`mediaType = "audiobook"`）是**两条独立的扫描链路**。

- 音乐链路走 `storage.MusicFS` 抽象 → 已经支持网盘了（M1–M3 完成）
- **有声书链路是另一套，现在还在直接读本地磁盘** → 这就是 M5 要干的事，见 §14

⚠️ 这是个坑：现在把网盘文件夹加成有声书库，**会静悄悄扫出 0 本书，而且不报错**。

### 0.6 技术栈一览

| 东西 | 技术 | 代码位置 |
|---|---|---|
| 服务端 | Go 1.26 + SQLite（Navidrome fork） | 仓库根目录 |
| Web 管理后台 | React + react-admin + Vite | `ui/` |
| 网盘网关 | OpenList（Docker） | 部署在 NAS，不在本仓库 |
| APP 端 | Kotlin + Jetpack Compose + Media3 ExoPlayer | 另一个仓库 `LeChenMusic-Player`，**本次改动不需要碰** |

> APP 端零改动的原因：它走的是标准 Subsonic API，服务端用 302 告诉它去哪拉流，
> ExoPlayer 本来就跟随 302。
> 范围：音乐（无损 FLAC / 普通格式）+ 有声书；**不含视频**（影视走 LunaTV 独立线）
> 部署环境：飞牛 NAS（fnOS），需要外网访问

## 0. 需求与目标

服务端支持**添加网盘文件夹**作为媒体源：直接扫描网盘里的音乐/有声书、直接播放网盘里的文件，
体验对齐"飞牛影视读网盘"的方式；扫描与播放尽量**不触发网盘风控**。

已确认的决策：
- 实现路线：**方案 B —— 索引 + 302 直链模式**（见 §2）
- 首个联调网盘：**阿里云盘**（已挂载）；夸克免费版随后跟进对比测试
- 最终目标：**夸克 / 115 / 百度 / 阿里四家都支持**（OpenList 架构下是配置级差异）
- 播放场景：家庭内网 + 外网访问

## 1. 背景：飞牛影视那套的原理

社区成熟链路（多篇教程交叉验证）：

```
飞牛影视 → 读取 .strm / 挂载目录 → OpenList → 302 跳网盘直链(CDN)
        → 播放器直接从网盘 CDN 拉流（媒体数据不经过 NAS）
```

飞牛影视不用 OpenList，是因为飞牛官方自研了这层（闭源，和 115/夸克有直链合作），对外没有接口，
无法复用。开源界的等价物就是 **OpenList**（AList 社区续作）。

参考项目：OpenList（OpenListTeam/OpenList）、alist-strm、emby2Alist、CloudDrive2、rclone。

## 2. 方案 B：索引 + 302 直链（定稿）

核心思想：**网盘内容只索引、不搬运**；能不读文件内容就不读。

```
添加网盘文件夹（OpenList 地址 + 路径）
  → 列表扫描：POST /api/fs/list 拿 名字/大小/mtime（纯 JSON，极轻）
  → 建库入库：文件名解析出 艺术家-标题（零文件读取）
  → 懒加载 tag/封面：需要时才对直链发 HTTP Range 取头部 256KB~2MB，解析后永久缓存
  → 播放：/rest/stream → POST /api/fs/get 拿 raw_url → HTTP 302 →
    App(ExoPlayer) 直连网盘 CDN 拉流，数据不经过 NAS
```

### 2.1 服务端改造点（对应 Navidrome fork 现有代码）

1. **配置/模型**：`model.ScanTarget` 增加 `Source` 类型（`local` / `openlist`）；
   云源记录 OpenList 地址、远端路径、凭据（放服务端配置，不入库）；
2. **scanner**：文件枚举抽象 `FileSource` 接口（Local=现有 Walk；Cloud=OpenList 分页列表）；
   tag 提取抽象成"Range 读取器"——云源只喂头部/尾部字节段给 taglib
   （M4A 封面可能在 moov 尾部，需尾部兜底）；
3. **stream**：`streamer.NewStream` 新增 `RedirectStream`——直链可用则 302；
   否则回退**中转流**，再叠加可选**转码流**（低速外网听无损的场景，复用现有 ffmpeg 管线）；
4. **封面/图片**：一律本地缓存（`cacheDir`），云源缺失时 Range 取一次；
5. **管理 API/UI**：媒体库添加页增加"网盘文件夹"类型。

### 2.2 直链的已知坑（必须有 fallback）

- 直链**有时效**（小时级）→ 每次播放现取，不长存；
- 部分网盘直链**绑定请求 IP/UA**（115/夸克部分场景、百度尤甚）→ 客户端可能拉不动 →
  自动回退服务端中转（App 无感知）；
- ExoPlayer/OkHttp 默认跟随 302 ✅，但**不要把服务端鉴权头转发到 CDN**；
- 百度直链要改 UA + 官方接口模式（仅 SVIP 可靠），免费/普通会员直接用中转回退。

## 4. 网盘风控规避设计（硬性要求）

**风险认知（丑话）**：2026-06 起各网盘收紧——115 治理公告把"第三方工具/脚本/非官方 API 批量操作"
列为技术红线（功能限制至封号）；夸克清理违规分享内容；百度有"hit black userlist"类反爬误伤。
**第三方方案没有零风险**，策略 = 自用、低调、模拟正常用户：

1. **通道**：不自写网盘爬虫，统一走 OpenList 驱动；单账号单实例；不混批量转存/分享/删除等管理操作；
2. **读取形态**：列表 API 建库；文件内容**懒读**；tag/封面**只 Range 局部读**；
   **永远不为扫描做全文件下载/哈希**；tag/封面/目录列表强缓存，mtime 未变不重读；
3. **播放形态**：302 直链 = 正常在线播放；**禁止多线程分段加速下载**（下载器特征）；
   直链过期重新解析；
4. **频率**：全局令牌桶（列表 ≤1 req/2s、内容读并发 1~2，可配置）+ ±20% 随机抖动；
   全量扫描放凌晨错峰，日间只增量；
5. **异常**：429/403/验证码 → 指数退避（≤3 次）→ 熔断 30 分钟快速失败并告警，**不硬刚**；
6. **账号**：登录态刷新节制、单会话；重要曲库元数据本地有库，网盘被清退可平滑换源。

### 5.1 实现与原方案的差异（重要）

1. **`FileSource` 抽象 → `storage` 注册表**
   原方案打算在 scanner 里另抽一个 `FileSource` 接口。实际实现发现仓库已有
   `core/storage` 注册表（`storage.Register(scheme, constructor)`）+ `MusicFS` 接口，
   scanner/artwork/封面全都吃 `storage.MusicFS`。因此改为注册 `openlist://` scheme，
   **scanner 一行没改**，云库只是"库路径写成 `openlist://host:port/远端路径`"。
   这是更小、更不容易出错的改造面。

2. **`model.ScanTarget` 未加 `Source` 字段**
   数据源类型由 `Library.Path` 的 scheme 隐式决定（`file` / `openlist`），
   不再冗余存一份。`storage.For()` 取不到实现时会直接报错。

3. **"文件名解析建库" vs "懒加载 tag" → 改成可配置的 `TagMode`**
   原方案是"扫库零读取、tag 全靠懒加载"。实测发现这样做库里没时长/码率/封面，
   体验太差。现改为：
   - `TagMode = "scan"`（**默认**）：扫描时用 Range **只读头部 2MB + 尾部 2MB** 取真实标签，
     有读取预算硬上限（默认 16MB），**永不整文件下载**；重扫时目录 hash 未变就不重读，
     等于 DB 本身就是"永久缓存"。
   - `TagMode = "filename"`：完全零内容读取，艺术家/专辑取自父目录、曲名取自文件名，
     秒建库，但没有时长/码率/封面。适合超大曲库或风控极严的网盘。
   标签解析失败时两种模式都会回落到文件名解析，保证库一定能建起来。

4. **转码回退的实现方式**
   原方案说"叠加可选转码流"。云库没有本地路径能喂给 ffmpeg，实际做法是
   **把直链当 ffmpeg 输入**（`-i <raw_url>`），ffmpeg 自己从网盘 CDN 拉流，
   既不用改造 ffmpeg 管线，媒体数据依旧不过 NAS。

联调环境（已就绪）：OpenList 已部署于飞牛 NAS → 首个网盘**阿里云盘**已挂载。
目录约定：`fnos/音乐/艺人/专辑/曲目`（解析规则按此两级父目录设计）。
**有声书**建议摆成 `fnos/有声书/书名/章节文件`，见 §7。

## 7. 有声书云源支持（M5）

> 硬需求：**音乐和有声书都要能放网盘**。本节记录现状缺口与改造方案。

### 7.1 现状缺口（为什么现在不行）

音乐链路走的是 `storage.MusicFS`，所以 M2 一上云源音乐就能用。
但有声书是另一条独立扫描链路，**它没走 storage 抽象**：

| 位置 | 现状调用 | 问题 |
|---|---|---|
| `scanner/audiobook_scanner.go:58` | `filepath.WalkDir(library.Path, ...)` | 直接扫本地磁盘 |
| `:74` `:210` `:304` | `os.ReadDir(path)` | 直接读本地目录 |
| `:183` `:242` | `os.Stat(coverFile)` | 直接 stat 本地文件 |
| `:248` `:318` | `os.Open(filePath)` | 直接打开本地文件 |

结果：把 `openlist://...` 当库路径加进去后，`filepath.WalkDir` 会当作普通目录名去扫，
**一个有声书都扫不到**（不会报错，只是静肳肳空扫），这是最难排查的一类问题。

### 7.2 改造方案（M5）

把有声书扫描器换成走 `storage.MusicFS`，本地/网盘一套代码：

| 现状 | 改为 |
|---|---|
| `filepath.WalkDir(library.Path, ...)` | `fs.WalkDir(fsys, ".", ...)` |
| `os.ReadDir(path)` | `fs.ReadDir(fsys, path)` |
| `os.Stat(p)` | `fs.Stat(fsys, p)` |
| `os.Open(p)` + `taglib.OpenStream(file, ...)` | `fsys.Open(p)` + `taglib.OpenStream(rs, ...)` |
| `filepath.Join(...)` | `path.Join(...)`（fs 路径用 `/`） |

关键点：`fsys.Open()` 返回的句柄在云源上就是 `core/cloudsource.remoteFile`，
它实现了 `io.ReadSeeker`，而 `taglib.OpenStream` 要的正是这个接口，**所以标签解析零改动**，
自动变成"只 Range 取头尾字节"的懒读取（含读取预算）。

改造入口：先在 `scanner/audiobook_scanner.go` 里拿 `storage.For(library.Path)` 取 `FS()`，
然后把四处裸调用替换掉。**本地库行为不变**（local 后端就是 `os.DirFS` 的包装）。

### 7.3 目录约定（有声书）

```
fnos/有声书/书名/01 章节名.m4b
fnos/有声书/书名/02 章节名.m4b
fnos/有声书/书名/cover.jpg        ← 封面（可选）
```

- 一级父目录 = **书名**，文件 = **章节**（与音乐的 艺人/专辑/曲目 两级约定对应）
- `mediaType` 填 `audiobook`（现有按名字/路径关键词自动识别：有声/audiobook/评书/相声/小说/戏曲）
- 封面支持 `cover/folder + jpg/jpeg/png`，云源上同样走 Range 懒读取 + 本地缓存

### 7.5 M5 实际改造范围（比 §7.2 多，重要）

§7.2 只列了 `scanner/audiobook_scanner.go` 的 4 处裸调用。实际做完扫描器才发现，
**播放和封面链路还有 3 处直接读本地磁盘**——不改的话书能扫进来但播不了、封面 404，
M5 等于白做。这 3 处也一并改了：

| 位置 | 原状 | 问题 |
|---|---|---|
| `server/nativeapi/audiobook.go` `stream()` | `http.ServeFile(filepath.Join(lib.Path, ...))` | **APP 实际走的就是这个接口**（`MusicRepository.kt:746`），网盘书播不了 |
| `server/nativeapi/audiobook.go` `cover()` | `os.Stat` + `http.ServeFile` | 网盘书封面直接 404 |
| `server/subsonic/stream.go` `Stream()` 的 audiobook 分支 | `fmt.Sprintf("%s/%s/%s")` + `http.ServeFile` | Subsonic 客户端播不了 |
| `server/subsonic/audiobook.go` `StreamAudiobookChapter()` | `filepath.Join` + `http.ServeFile` | 同上 |

**统一入口**：新增 `core/storage/serve.go` 的 `ServeFile()`，降级阶梯与音乐链路一致（§2.2）：

1. 云源拿到直链 → **302**（只写 Location 头，不写响应体、不记日志）
2. 拿不到 → 服务端中转，`http.ServeContent` 保留 Range/seek
3. 本地库 → 同一条代码路径（`os.DirFS` 包装），行为不变

另外新增 `storage.FSFor()` / `storage.DirectURL()` 两个辅助函数，
把“怎么拿到一个库的 FS / 直链”收成一处，免得每个调用点各写一遍
`For()` + `ContextualStorage` 断言。

**顺便修掉的存量 bug**：新建书时 `scanChapters()` 算完 `ChapterCount` / `TotalDuration` /
`Size` 写在内存对象上，但**从来没有 `Put` 回数据库**（只有“更新”分支会存）。后果是 API 一直
返回 0 章节，而且 `ChapterCount == 0` 这个判断让**每次扫描都重读全部章节标签**（云盘上就是
每次都打一串 Range 请求）。现在建书后补一次 `Put`。

### 8.1 Docker 部署时配置文件放哪（2026-09-26 首次联调踩坑，下次照抄）

`navidrome.toml` 是**独立配置文件**，需要手动新建，不在 compose 里；compose 的 `./data` 是
**相对于 compose 项目目录**的，fnOS 上实际位置可能和预期不一样。首次联调时配置建错了位置，
后台测试连接报 `cloudsource: no OpenList gateway configured`（= 服务端没读到任何 `[OpenList.*]`）。

```bash
# ① 先查 /data 真实映射到宿主机哪里
​docker inspect <容器名> --format '{{range .Mounts}}{{.Source}} => {{.Destination}}{{"\n"}}{{end}}'

# ② 在查到的目录里建 navidrome.toml（如 /vol2/1000/Docker/lechen-music/data/navidrome.toml）

# ③ 验证文件挂进去了（能打出来才继续）
docker exec <容器名> cat /data/navidrome.toml

# ④ 重启（配置只在启动时读一次）
docker restart <容器名>
```

**避坑清单**：① 文件放 `docker inspect` 查出来的目录，别猜；② 改配置必须重启容器；
③ TOML 段名必须两段式 `[OpenList.nas]`；④ OpenList `URL` 写**局域网 IP**，别写 `127.0.0.1`
（容器里的 localhost 是容器自己，必连不通）。

## 9. 工程化 / CI 现状

排查中发现的几个工程问题与决策：

1. **上游的 Test/Lint 流水线从来没跑过**
   `.github/workflows/pipeline.yml`（Test、Lint、Build）触发分支写的是 `master`，
   本仓库是 `main`，所以它一次都没执行过。目前实际只有 `build.yml` 在跑，
   而它只做 `go build -o navidrome .`，**不跑任何测试**。

   **决策：不把 `pipeline.yml` 的分支改成 `main`。** 那是上游 Navidrome 的完整发布流水线，
   里面带着发布、Docker 镜像推送、翻译回传等动作，盲目打开会连带触发一串不可控的事。
   改为**新增一个精简的 `test.yml`**：push / PR 到 `main` 时只跑 `go vet` + `go test`，
   纯质量门禁，无副作用。（前提是全量测试本地先确认是绿的，否则 CI 一上来就是红的。）

2. **`tests/navidrome-test.toml` 被 `.gitignore:29` 的 `navidrome-*` 忽略**
   所以新开发者 clone 下来直接 `go test ./...` 会 FATAL。需要自建一份（见 §8 之外的
   本地开发说明）。已在本地补齐。

3. **`tests/mock_data_store.go` 曾经缺失 `PlayLog`/`UserDevice` 实现**
   导致 `tests` 包编译失败，连带所有依赖它的包都跑不了测试（已修，78bf7c3）。
   根因是 mock 未随接口同步更新，而 CI 不跑测试所以没被发现——这也是第 1 条要补 CI 的理由。

### 10.3 已知未决 / 需要注意

1. **跑测试依赖本地 `tests/navidrome-test.toml`**（被 `.gitignore:29` 的 `navidrome-*` 忽略）：
   新环境 clone 下来 `go test ./...` 会直接 FATAL，要自建一份，见 §9.2。
2. **转码回退的边界**：目前是把直链当 ffmpeg 输入，而直链是**小时级有效**的。
   超长音频（几小时的有声书章节）转码到一半可能断流。M5 做有声书时必须一起验这个边界，
   不行就改成"先把远端流灌给 ffmpeg stdin"（`ffmpeg.start` 已支持传入 `io.Reader`，改造面很小）。
3. **风控没有零风险方案**。上线初期请盯一下服务端日志里的 429/403/验证码，
   触发熔断（默认 30 分钟）时不要硬重试，见 §4。
4. **TagMode 的选择**：默认 `scan`（首次扫描会按 Range 逐个取标签，曲库大时耗时较长但只此一次）；
   如果嫌慢或网盘风控严，切 `TagMode = "filename"` 秒建库（代价是没有时长/码率/封面），见 §5.1。
5. **有声书章节播放是 raw-only（不转码），这是有意的**：改造前就是 `http.ServeFile` 裸出文件，
   客户端传 `format` 也不会转。M5 改走 `storage.ServeFile` 后保持这一点，以免给本地老用户
   引入意外的转码（红线：本地库行为不变）。因此 §7.4 最后一条“长章节转码不断流”**不适用**：
   不走 ffmpeg，也就不会碰 §10.3② 的直链过期断流问题（302 是每次播放现取的）。
   如果以后要支持有声书转码，应该走 `core/stream.NewStream` 并把直链过期边界一起解掉。
6. **网盘封面没有本地磁盘缓存**：`cover()` 靠 `Cache-Control: max-age=3600` + `http.ServeContent`
   的 `If-Modified-Since`（304）省流量，云源上能拿直链时直接 302 给客户端。曲目量大了可以
   参照 `core/artwork` 的缓存加上磁盘缓存，目前先不做。

### 13.3 `path` 组合规则（必须和后端 `BuildURI()` 对齐）

后端唯一真相源是 `core/cloudsource/storage.go` 的 `BuildURI()`：

- 从地址里取 **`host:port`**（丢掉协议前缀和末尾 `/`），转小写
- 远端路径去掉首尾 `/`
- 拼成 `openlist://<host:port>/<remotePath>`，**每个路径段单独 URL 转义**

前端参考实现（可直接用）：

```js
export const buildCloudPath = (address, remotePath) => {
  let host = String(address || '').trim().replace(/\/+$/, '')
  host = host.replace(/^[a-z][a-z0-9+.-]*:\/\//i, '')   // 丢掉 http:// 等
  host = host.split(/[/?#]/)[0].toLowerCase()          // 只留 host:port
  const path = String(remotePath || '').replace(/^\/+|\/+$/g, '')
  if (!host) throw new Error('OpenList address is required')
  return path ? `openlist://${host}/${path.split('/').map(encodeURIComponent).join('/')}`
              : `openlist://${host}`
}

// buildCloudPath('http://192.168.1.10:5244', 'fnos/音乐')
// → 'openlist://192.168.1.10:5244/fnos/%E9%9F%B3%E4%B9%90'
```

⚠️ 常见坑：
- 中文要转义（`音乐` → `%E9%9F%B3%E4%B9%90`），但**只能转义一次**（后端 `BuildURI` 会再做一次，
  前端如果自己 `encodeURIComponent` 了整个路径会双重转义）——用上面“逐段转义”写法就是对的
- 回显（编辑时）要把 `path` 拆回两个字段：`new URL(path.replace('openlist://', 'http://'))` 或手动 split

## 14. 任务说明书 B：M5 有声书云源支持（✅ 已完成 2026-09-25）

> 目标：让**网盘上的有声书**能被扫进来。
> 现状：**扫不出来，而且不报错**（静默失败），因为扫描器直接读本地磁盘。

### 14.1 调用链（先看懂这个）

```text
scanner/scanner.go  （总调度，跑 5 个阶段）
  └─ scanner/phase_5_audiobooks.go:30
       └─ scanner := NewAudiobookScanner(p.ds)
          scanner.ScanLibrary(p.ctx, lib)          ← lib.Path 现在可能是 openlist://...
             └─ filepath.WalkDir(library.Path, …)  ← ❌ 把 URI 当成本地目录，于是扫出 0 个
                └─ createAudiobookFromDir()   建书（书名 = 一级目录）
                   └─ scanChapters()          建章节 + taglib 读时长
```

数据模型（`model/audiobook.go`）：

- `AudiobookChapter`：`Title`/`ChapterNumber`/`Duration`/`Format`/`FileSize`/**`Path`**
- `AudiobookProgress`：播放进度、倍速、跳过片头片尾、是否听完（**云源上也要能用**）

### 14.2 改造点（4 处裸调用 → 走 `storage.MusicFS`）

⚠️ **本节的 4 处只是扫描器**。播放/封面链路还有 3 处裸调用，不改的话书扫进来也播不了，
完整清单见 **§7.5**。

| 现状 | 行号 | 改为 |
|---|---|---|
| `filepath.WalkDir(library.Path, func(path string, d os.DirEntry, …))` | `:58` | `fs.WalkDir(fsys, ".", func(path string, d fs.DirEntry, …))` |
| `os.ReadDir(path)` | `:74` `:210` `:304` | `fs.ReadDir(fsys, path)` |
| `os.Stat(coverFile)` / `os.Stat(chapterPath)` | `:183` `:242` | `fs.Stat(fsys, coverFile)` |
| `os.Open(filePath)` + `taglib.OpenStream(file, …)` | `:248` `:318` | `fsys.Open(filePath)` + `taglib.OpenStream(rs, …)` |
| `filepath.Join(...)` | 多处 | `path.Join(...)`（`io/fs` 的路径用 `/`） |
| `filepath.SkipDir` / `filepath.Ext` | 多处 | `fs.SkipDir` / `path.Ext` |

**怎么拿 `fsys`**（照抄 `core/library.go` 或 `server/nativeapi/cloudsource.go` 里的写法）：

```go
st, err := storage.For(library.Path)          // 本地库/网盘库同一行代码
if err != nil { return err }
var fsys storage.MusicFS
if cs, ok := st.(storage.ContextualStorage); ok {
    fsys, err = cs.FSWithContext(ctx)          // 云源：可取消，别用旧的 FS()
} else {
    fsys, err = st.FS()
}
```

### 14.3 为什么 taglib 那边一行都不用改

`fsys.Open()` 返回的句柄在云源上就是 `core/cloudsource.remoteFile`，
它实现了 `io.ReadSeeker` —— 而 `taglib.OpenStream` 要的正是这个接口。

所以标签解析自动变成“**只 Range 取头尾字节 + 读取预算**”，不会整文件下载。

⚠️ 但要**验证**：几小时长的 `.m4b` 章节，时长能不能读对。
如果读不对，多半是文件太大、头 2MB 取不到完整标签——调大 `HeadBytes`/`TailBytes`（§8）再试。

### 14.4 目录约定（有声书）

```text
fnos/有声书/书名/01 章节名.m4b
fnos/有声书/书名/02 章节名.m4b
fnos/有声书/书名/cover.jpg        ← 封面（可选，也支持 folder.png 等）
```

- 一级目录 = **书名**（对应 `Audiobook.Title`），文件 = **章节**（`ChapterNumber` 按文件名排序）
- `mediaType` 填 `audiobook`；现有代码会按关键词自动识别：有声 / audiobook / 评书 / 相声 / 小说 / 戏曲
- **原 helperText “有声书库填 `/audiobooks`”是旧约定，已确认不适用并删掉**：
  媒体类型是靠 `core/library.go` 的 `detectMediaType(name, path)` 按**名称/路径关键词**自动识别的，
  路径叫什么都行。现在换成了 `resources.library.helpers.path` 这条翻译文案，说明这个机制。

## 15. 红线与自检清单

### 15.1 绝对不要做（做了会出事）

| 红线 | 为什么 |
|---|---|
| ❌ **不要为了扫描去整文件下载 / 算哈希** | 几 TB 流量 = 网盘风控封号。读取预算是硬限制（`MaxTagReadBytes`），别绕过它 |
| ❌ **不要开多线程分段下载** | 那是下载器特征，必被风控。Range 读取是**单流、节流、带抖动**的 |
| ❌ **不要把签名 URL 写进日志 / 响应体** | 那是临时凭据，谁拿到谁能下文件。`remoteFile.String()` 已故意不打印它 |
| ❌ **不要把网盘凭据写进数据库或前端** | 只能放服务端配置（§8）。`OpenListOptions.Password/Token` 已经 `json:"-"`，别删这个标记 |
| ❌ **不要把服务端鉴权头转发给网盘 CDN** | 302 由客户端自己跳，我们不代理请求头 |
| ❌ **不要改 `.github/workflows/pipeline.yml` 的分支名** | 那是上游的发布流水线（带 Docker 推送/翻译回传），打开会连带触发一堆事，见 §9.1 |
| ❌ **不要用 `OpenList` 的 `refresh=true`** | 会绕过网关自己的缓存，多打上游（`adapters/openlist/types.go` 的 `listRequest.Refresh` 保持 false） |
| ⚠️ **遇到 429/403/验证码不要硬重试** | 会指数退避 3 次然后熔断 30 分钟，这是**设计如此**，别改成无限重试 |
