# 在线搜歌下载功能 · 开发文档

| 项目 | 内容 |
|------|------|
| 功能名称 | 在线搜歌下载（缺歌自动补齐） |
| 状态 | 开发中 |
| 创建日期 | 2026-11-14 |
| 涉及仓库 | LeChenMusic-Server（主）、LeChenMusic-Player（APP 端） |
| 里程碑进度 | 见 [第 10 节](#10-开发进度) |

---

## 1. 背景与目标

用户在 APP 端 / 网页管理后台搜索歌曲时，如果服务器曲库没有这首歌，目前只能：手动去第三方网站下载 → 手动刮削（封面/歌词/标签）→ 手动放入 NAS 目录。流程繁琐。

**目标**：在 Web 管理后台（后续 APP 端）输入"歌名 + 歌手"即可完成 **在线搜索 → 选择音质 → 下载到服务器 → 自动刮削（封面/歌词/歌曲信息）→ 自动入库** 的全流程。用户刷新即可播放。

## 2. 需求确认（已拍板）

| # | 需求点 | 结论 |
|---|--------|------|
| 1 | 使用场景 | 纯家人使用、非商用、私有 NAS，不做公网分发 |
| 2 | 去重/模糊匹配 | 服务器端提供**模糊匹配开关**（用户自由选择）；开启后允许下载其他版本（Live、翻唱等） |
| 3 | 音质策略 | 默认 FLAC；无 FLAC 自动降级 MP3（优先 320k，再次 128k） |
| 4 | 入口位置 | 首期做**网页管理后台**；当前手动流程迁入后台，输入歌名+歌手 → 自动下载+刮削+存放 |
| 5 | 权限控制 | 暂不限制（家人使用）；**但提供可选权限方案**（见 6.8），由管理员决定是否启用 |
| 6 | 有声书 | 后续阶段支持"搜不到就下载"模式，资源源调研后确定 |
| 7 | 部署环境 | NAS、千兆下行 / 约 70Mbps 上行；下载并发与带宽占用需可控 |

## 3. 默认设计决策（可后调）

| 事项 | 默认方案 |
|------|----------|
| 存放目录 | 媒体库根目录下 `Artist/Album/Track-Title.ext`（与现有扫描器约定一致，自动入库） |
| 文件命名 | `01 - 曲名.flac`；非法字符清洗（`\/:*?"<>|`）；同名冲突追加 `(2)` |
| 标签写入 | **全部内嵌进音频文件**：标题/歌手/专辑/年份/音轨号（FLAC Vorbis Comment / MP3 ID3v2.4） |
| 封面 | **内嵌**到音频文件（FLAC PICTURE 块 / MP3 APIC 帧），**不生成** `cover.jpg` |
| 歌词 | **内嵌**到音频文件（FLAC `LYRICS` 字段 / MP3 `USLT` 帧），**不生成** `.lrc`；服务端现有读取链路（gotaglib USLT/SYLT）直接兼容 |
| 重复下载 | 默认拒绝（歌名+歌手归一化后精确匹配已有曲目）；用户开启模糊匹配后放行 |
| 试听/中间文件 | 下载到 `data/downloads/tmp/`，完成后原子移动进媒体库，失败自动清理 |
| 下载并发 | 默认 1 个任务同时下载（NAS 写盘友好），可配置 |
| 站点限速 | 对解析站请求间隔 ≥ 2s，失败指数退避，最多重试 3 次 |

## 4. 合规与风险声明

> **必读**

1. 本功能面向**纯私人/家庭用途**（非商用、非公开分发）。音频资源来自第三方聚合解析站点，版权归属原作者及发行方。
2. **严禁**将本功能用于商用、对外提供服务或公开分发下载内容；由此产生的法律风险由部署者自行承担。
3. 上游站点（`flac.music.hi.cn`）为无 SLA 的第三方服务，接口可能随时变更或失效。架构上通过**下载源适配器**隔离，可替换来源或自建解析服务。
4. 系统默认仅登录用户可用；权限方案（6.8）建议至少启用"仅管理员可下载"。

## 6. 服务端设计

### 6.1 下载源适配器

新增包 `server/online/`：

```go
// server/online/source.go
type Source interface {
    Name() string
    DisplayName() string
    SearchSong(ctx context.Context, req SearchRequest) (*SearchResult, error)
    ResolveURL(ctx context.Context, song SongRef, quality Quality) (*ResolvedMedia, error)
    GetLyrics(ctx context.Context, song SongRef) (string, error)
}

type SearchRequest struct {
    Keyword  string // 歌名 + 歌手
    Page     int
    PageSize int
}

type SongRef struct {
    Source   string // "hicn"
    Platform string // 上游平台：kuwo / qq / ...
    ID       string
    Time     int64  // 上游签名参数
    Sign     string
}

type Quality struct{ Format string; Bitrate int } // flac/2000, mp3/320, mp3/128

type ResolvedMedia struct {
    URL      string
    Format   string
    Bitrate  int
    Size     int64
    Duration int
}
```

**`server/online/hicn.go`**（首个实现）：对接 `flac.music.hi.cn` 的 PHP 接口（已实测还原）：

| 动作 | 端点 | 参数 | 说明 |
|------|------|------|------|
| 搜索 | `POST ajax.php?act=search` | `platform, keyword, page, size` | 返回歌名/歌手/专辑/封面 `pic_url`/时长/音质档位 `minfo`/`time`/`sign` |
| 取直链 | `POST ajax.php?act=getUrl` | `platform, songid, format, bitrate, time, sign` | 返回音频直链（上游 CDN） |
| 歌词 | `POST ajax.php?act=getLyric` | `platform, songid, time, sign` | LRC 歌词 |

- 所有请求带 `Referer: https://flac.music.hi.cn/`，间隔 ≥ 2s（`httprate` 或内部限速器）。
- 直链与搜索结果本地缓存 1h（与站点前端行为一致），减少对上游压力。
- 接口协议变更仅影响 `hicn.go` 一个文件；后续可增补自建解析源（Meting-API 兼容）等。

### 6.2 搜索与模糊匹配

- 搜索关键词统一为"歌名 + 歌手"（用户输入两个字段，拼接发送给上游）。
- **去重判定**：对曲库做"歌名 - 歌手"归一化（去空白/全半角/大小写/括号备注如 `（Live）` 可配置是否忽略）后匹配。
  - 开关关闭（默认）：曲库存在精确匹配 → 拒绝下载，提示"曲库已有"。
  - 开关开启：展示所有搜索结果（含不同版本），用户可任意下载。
- 搜索结果中与曲库重复的条目打上"已收录"标记，前端置灰。

### 6.3 音质策略

用户选择"默认"时按优先级尝试：`flac 2000k` → `mp3 320k` → `mp3 128k`，取直链失败（或无该档位）自动降级并在任务日志记录实际音质。用户也可手动指定某一档位。

### 6.4 下载任务系统

- 新增表 `download_task`：

| 字段 | 说明 |
|------|------|
| id / user_id | 任务与发起人 |
| song_name / artist / keyword | 用户输入 |
| source / platform / source_song_id / sign / time | 上游定位信息 |
| quality / actual_format / actual_bitrate | 期望音质 / 实际音质 |
| status | `queued → resolving → downloading → tagging → done` / `failed` |
| file_path / file_size / error | 结果与失败原因 |
| created_at / updated_at / finished_at | 时间线 |

- 后台 worker 消费队列（并发默认 1，可配）；任务进度按已下载字节数上报（前端进度条）。
- 失败自动清理临时文件；任务可重试（保留原参数）。
- 磁盘空间预检：`minfo` 提供文件大小，空间不足直接失败并提示。

### 6.5 入库与刮削

下载完成后编排（内嵌式刮削，**不产生任何外部文件**）：

1. 确定目标路径 `Artist/Album/Track - Title.ext`（目录不存在则创建）；
2. **歌曲信息**：写入内嵌标签（标题/歌手/专辑/年份/音轨号）；
3. **封面**：内嵌到音频文件（FLAC PICTURE 块 / MP3 APIC 帧），来源为搜索结果 `pic_url`（可选升级为刮削源的高清封面）；
4. **歌词**：内嵌到音频文件（FLAC `LYRICS` / MP3 `USLT`）；优先 `getLyric`，失败则走现有刮削源（网易云/QQ/酷狗/酷我）补抓；
5. 原子移动到媒体库，触发扫描入库（复用现有 scanner 触发机制）。

**标签写入实现**（新增依赖，均为纯 Go）：

| 格式 | 库 | 写入内容 |
|------|----|----|
| MP3 | `github.com/bogem/id3v2` | TIT2/TPE1/TALB/TYER/TRCK + APIC + USLT |
| FLAC | `github.com/go-flac/go-flac` + `flacpicture` | Vorbis Comment + PICTURE + LYRICS |

> 为什么不落外部文件：自用生态（自家服务端+自家 APP）完全读内嵌标签；目录保持干净，避免刮削文件与媒体文件不同步。如个别第三方 Subsonic 客户端不读内嵌歌词，后续可加可配置降级（默认关）。

### 6.6 API 设计（native API）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/online/search?keyword=&page=&size=` | 在线搜索（返回条目 + 是否已收录 + 可选音质） |
| POST | `/api/online/download` | 创建下载任务 `{source, platform, songId, quality, fuzzy}` |
| GET | `/api/online/tasks?mine=` | 任务列表（状态/进度） |
| POST | `/api/online/tasks/{id}/retry` | 重试失败任务 |
| DELETE | `/api/online/tasks/{id}` | 删除任务记录（仅 queued/failed） |
| GET | `/api/online/downloads?user=&q=&scrape=` | **管理员**：全部用户下载记录（含刮削状态） |
| GET | `/api/online/downloads/{id}/verify` | **管理员**：读取文件内嵌元数据实况（刮削验证） |
| DELETE | `/api/online/downloads/{id}` | **管理员**：删除下载歌曲（文件+曲库记录+任务记录） |
| POST | `/api/online/downloads/{id}/rescrape` | **管理员**：重新刮削（重抓封面/歌词/标签，重写内嵌元数据） |
| GET | `/api/online/logs?type=&user=&page=` | **管理员**：操作日志 |
| DELETE | `/api/online/logs` | **管理员**：清空操作日志 |

权限：所有接口需登录；下载类接口受 6.8 权限方案控制；`/api/online/downloads*`、`/api/online/logs*` 为管理员专属。

### 6.7 配置项（`Configuration`）

| 配置 | 默认 | 说明 |
|------|------|------|
| `EnableOnlineDownload` | `true` | 总开关 |
| `OnlineDownloadQuality` | `flac-preferred` | 音质策略 |
| `OnlineDownloadConcurrency` | `1` | 下载并发 |
| `OnlineDownloadMinIntervalMs` | `2000` | 上游请求最小间隔 |
| `OnlineDownloadPermission` | `admin-or-approved` | 权限模式（见 6.8） |
| `OnlineDownloadDailyQuota` | `0`（不限） | 每用户每日下载上限（首） |
| `OnlineDownloadLibPath` | 媒体库根目录 | 下载存放的媒体库 |

### 6.8 权限方案（可选启用，三选一）

| 模式 | 说明 | 适用 |
|------|------|------|
| `open` | 任何登录用户可搜索、可下载 | 纯家庭互信（当前默认场景） |
| `admin-or-approved`（**默认**） | 仅管理员可下载；普通用户可搜索并发起申请，管理员在任务列表一键批准后执行 | 推荐 |
| `quota` | 登录用户均可下载，但限每人每日 N 首 + 限速 | 用户较多时 |

> 建议：即使家用，也至少启用 `admin-or-approved`，防止误操作打满磁盘。

## 7. Web 管理后台设计

### 7.1 「在线搜歌」页面（仅登录可见）

新增页面「在线搜歌」（侧边栏入口）：

- 顶部表单：歌名、歌手、模糊匹配开关、音质选择（默认/FLAC/MP3 320/128）；
- 结果列表：封面、歌名、歌手、专辑、时长、可选音质（含大小）、"已收录"标记、`下载` 按钮；
- 下载任务面板：进行中任务（进度条）、已完成、失败（可重试/删除）；
- 后台轮询 `/api/online/tasks`（3s），任务完成 toast 提示"已入库，可播放"。

**实现（M5，已完成）**

- 文件：`ui/src/online/OnlineSearchPage.jsx`；路由 `/online-search`（`ui/src/routes.jsx`），侧边栏「🎵 在线搜歌」所有登录用户可见；
- 调用 API：`GET /api/online/search`、`POST /api/online/download`、`GET /api/online/tasks?mine=1`、`POST /api/online/tasks/{id}/retry`、`DELETE /api/online/tasks/{id}`；
- 结果卡：封面（无封面用占位图标）、平台/时长/音质 chip；「已在曲库」的条目置灰，未开模糊匹配直接下载会被后端 `409` 挡住，页面展示后端原文案提示；
- 任务面板按 `active / failed / done` 三组渲染（`queued|resolving|downloading|tagging` 归入进行中，进度按 `progressBytes/totalBytes` 计算），失败卡展示 `error` 并可重试/删除；
- 轮询用 `useCallback` + `setInterval(3000)`；**首次轮询只登记已完成任务 id、不弹 toast**，避免打开页面时对历史任务重复提示；toast 4s 自动清除。

### 7.2 「下载管理」页面（仅管理员，M5 新增）

> 目的：管理员登录后台可以查看**所有用户下载的歌曲**，用于查看验证下载的歌曲及刮削（封面/歌词/标签）是否准确；刮削不准确的手动点击**重新刮削**；确认错误/无用的直接**删除**。

- 入口：侧边栏「下载管理」，仅管理员可见（非管理员访问 403）；
- 列表：全部用户的下载记录（`download_task` 中 `status=done`），列：
  - 下载用户、歌名、歌手、专辑、实际音质、文件路径、下载/完成时间；
  - 刮削状态徽标：封面 ✓/✗、歌词 ✓/✗、标签 ✓/✗（按文件实况判定）；
- 筛选：按用户、按歌名/歌手关键词、按刮削状态；
- **刮削验证面板**（点开单条）：读取音频文件**内嵌元数据实况**展示——
  标题/歌手/专辑/年份/音轨号、封面缩略图、歌词预览，供人工核对刮削准确性；
- 操作：
  - **删除**：删除音频文件 + 曲库记录 + 任务记录（操作日志保留审计痕迹），触发重扫使曲库立即生效；
  - **重新刮削**：对该文件重新执行刮削流程——重新抓取封面/歌词/标签并**重写内嵌元数据**（不动音频流、保留播放记录），支持手动修正歌名/歌手/专辑后再写入；完成后触发重扫并刷新验证面板；
  - 批量：可多选批量删除 / 批量重新刮削（M5 首版先做单条，批量列入 M8 打磨项）。

**实现（M5，已完成）**

- 文件：`ui/src/online/DownloadManagePage.jsx` + 服务端 `server/nativeapi/online_admin.go`；路由 `/online-downloads`，侧边栏「📥 下载管理」仅在 `permissions === 'admin'` 时显示；接口组由 `adminOnlyMiddleware`（`server/nativeapi/native_api.go`）保护，非管理员直接 `403`；
- 列表：`GET /api/online/downloads?user=&q=&scrape=&offset=&limit=`，只返回 `status=done`；服务端逐条回读文件内嵌元数据生成刮削徽标（封面 `hasCover`、歌词 `lyrics`、标签看标题/歌手是否存在），文件已不在磁盘时置「文件缺失」；排序按 `finishedAt`，为空回落 `createdAt`；分页 50 条/页（`limit` 默认 100、上限 200）；
- 筛选：`user` 匹配「用户 ID + 用户名」、`q` 匹配歌名/歌手/专辑、`scrape` 取值 `ok` / `missing-cover` / `missing-lyrics` / `missing-tags`；
- 验证面板：`GET /api/online/downloads/{id}/verify` 返回 `{task, userName, exists, metadata, coverUrl, error}`；封面以 `data:` URI 内联返回（无封面不返回该字段）；文件缺失或标签不可读时用 `error` 说明原因，不以 5xx 报错；
- 删除：`DELETE /api/online/downloads/{id}` —— 删音频文件 → 删曲库记录（按 `path` 预筛后用 `AbsolutePath()` 精确比对）→ 删任务记录 → 触发重扫；返回 `{deletedFile, deletedDb, warnings}`，某步失败只记 `warnings`、不回滚已完成步骤；操作日志保留审计痕迹；
- 重新刮削：`POST /api/online/downloads/{id}/rescrape`，body `{title,artist,album,coverUrl}` 全部可选，字段优先级 **请求 > 文件现值 > 任务值**；重抓封面/歌词，抓取失败则保留文件原有封面/歌词，随后重写内嵌标签（不动音频流、不改文件路径），同步修正任务记录中的歌名/歌手/专辑，触发重扫并返回 `{info, coverFetched, lyricsFetched}`，面板就地刷新。

### 7.3 操作日志（M5 新增）

- 新增表 `online_op_log`，记录在线下载子系统的全部关键操作：
  `download_queued` / `download_done` / `download_failed` / `delete` / `rescrape`，
  字段：操作人、操作类型、目标歌曲、结果（成功/失败+原因）、时间；
- 「下载管理」页内置日志页签：按操作类型/用户/时间筛选，支持一键清空（仅清空日志，不动下载记录）；
- 下载发起/完成/失败由任务系统自动落日志；删除/重新刮削由管理操作落日志。

**实现（M5，已完成）**

## 14. M5.2 「歌曲刮削」独立功能（2026-11-15）

把原“下载管理 → 重新刮削”的能力泛化为**曲库歌曲刮削**，独立菜单入口（仅管理员）：

```
🛠 歌曲刮削  (/song-scrape)
├─ 筛选：歌名 / 歌手（分页表格）
├─ 多选：☐ 全选本页 / ☐ 单选 → [批量刮削选中（N）]
├─ 单曲：[刮削] → 对话框（可修正 标题/歌手/专辑 后刮削）→ 结果展示
└─ 批量：逐首顺序执行 + 随机间隔 0.8–1.8s + 进度条 n/total
```

**刮削流程**（`Ingestor.ScrapeSong`，复用 M3 内嵌写入 + M5.1 清洗）：

1. 读文件现有内嵌元数据；
2. 以「标题+歌手」在线搜索，**最佳匹配打分**（归一化标题+歌手精确=100，标题匹配+歌手重合=60+15/人，低于 60 不匹配）；
3. 命中则拉封面 + 歌词，专辑为空时用匹配结果补全；
4. **合并策略**：新值优先，抓不到的字段保留文件原值（绝不把原有封面/歌词清空）；
5. 重写内嵌标签（不动音频流、不改文件名）→ 触发曲库扫描刷新。

**API**：`POST /api/scrape/song/{id}/scrape`（body 可选 `title/artist/album` 修正词；admin-only）。

**技术要点**：

- 在线搜索/封面/歌词复用 `online.Source` 适配器（换源自动跟随）；
- 批量在前端顺序循环单曲接口（逐首反馈、失败不中断），请求间随机间隔防风控；
- 单测：最佳匹配打分、完整刮削链路（清洗标题/规范歌手/封面歌词内嵌）、无匹配时仅清洗关键词写入。

| 4 | 库中已有（如「从不喜欢孤单一个」）却不提示已收录 | 去重 SQL 预过滤用整串歌手 LIKE（搜“苏永康&彭佳丽” vs 库“苏永康 • 彭佳丽”永不命中） | 去重改为：**仅标题**进 SQL 候选 + Go 侧歌手**交集判定**（`ArtistsMatch`，共有任一歌手即命中；格式差异（& / • 、）归一化后互通） |

> 实测依据（WEB 端曲库）：`从不喜欢孤单一个` → `artist='苏永康 • 彭佳丽'`；按单人“苏永康”精确匹配才不会漏判。

**歌手格式规范**（全链路统一）：

- 写入标签/入库展示：`A • B • C`（`NormalizeArtist`/`NormalizeAlbumArtist`）；

## 17. 试听功能 + 上游 128k 占位片段问题（2026-11-16）

### 17.1 评估结论：搜歌结果可以加试听，已实现（WEB + APP）

上游 `getUrl` 能解析出可直接播放的临时直链（腾讯 COS，匿名可播、无 Referer/CORS 限制），
因此试听无需代理：服务端解析 URL，客户端 `<audio>` / `MediaPlayer` 直接流式播放。

**API**：`POST /api/online/preview`（登录可搜即可试听）
`{source, platform, songId, time, sign}` → `{url, format, bitrate, duration, expires}`

- **WEB**（在线搜歌结果行）：「试听」按钮 ↔「停止」切换，全局同时只播一首；
- **APP**（在线搜歌结果行）：▶/⏹ 按钮，`MainViewModel.togglePreview` 独立 `MediaPlayer`，
  与主播放器互斥（主播放器开播自动停试听），离开页面自动释放。

### 17.2 上游 quirk：mp3/128 是「试听占位片段」，不是真曲（实测）

`bitrate=128` 的 `getUrl` 对**任何歌曲**都返回同一段 12 秒占位音频
（songid 661178187，md5 与歌曲无关）；`bitrate=320` 才返回真曲，
且对只有 128k 档的歌会自动降档返回真实 128k 全曲（duration 正常）。

**处置**：

- `DefaultQualityChain` 移除 `mp3/128`（此前下载链路 128 兜底存在下载到 12 秒片段的隐患）；
- `hicnSource.ResolveURL` 源级兜底：`mp3/128` 请求自动改写为 `mp3/320`；
- 试听默认 `mp3/320`；WEB 音质下拉移除「MP3 128k」选项。

## 18. 问题修复：上游广告占位音频混入库 / 试听播广告（2026-11-18）

### 18.1 现象（实测复盘）

下载或试听几首之后，入库的文件不是歌曲，而是一段**固定的语音广告**（实测两首中招：
`真心 - 叶蒨文`、`不要说走就走 - 郭峰`，两个文件的音频逐字节一致）：

- 内容：酷我音乐口播广告——"酷我音乐已为您开启免费听歌权限，看广告免费畅听千万曲库，手机端可在应用商店获取……"；
- 特征：12.77s / 48kbps MP3 / 76979 字节，去标签后音频帧 md5 相同（同一份广告素材）；
- 命中时 `getUrl` 响应为 `format=mp3, bitrate=1`（请求的即使是 `flac/2000` 也返回这个），
  任务表里的痕迹就是 `actualBitrate=1` + 文件仅 12s；
- **间歇性**：几分钟后同一首歌又能解析出真曲，疑为上游"看广告送听歌"的风控/推广策略。

### 18.2 根因

下载链路对上游 `getUrl` 的返回值**完全信任**：解析出什么就下载什么、下载到什么就入库什么，
没有任何"这是不是这首歌"的校验；试听链路同样把直链原样交给客户端播放。

### 18.3 修复（三道防线：命中即重试，持续异常宁可任务失败也绝不入库）

| # | 防线 | 位置 | 判定依据 |
|---|------|------|----------|
| 1 | 解析结果可信度校验 | `online.ResolvePlausible`（`server/online/validate.go`） | `bitrate < 32`（广告实测 = 1）；`duration` 与歌曲期望时长偏差 > max(20s, 15%)；无期望时长时 `duration < 20s` |
| 2 | 下载完成后真实时长复核 | `online.ValidateDownloadedAudio` + `AudioDuration`（`server/online/audiodur.go`，纯 Go 解析 FLAC STREAMINFO / MP3 帧链） | 文件真实音频时长 vs 歌曲期望时长（同容差）；无期望时长时 < 20s 拒绝 |
| 3 | 重试与放弃 | `Manager.run` 重试环 + `hicnSource.InvalidateURL` | 命中 → 清直链缓存 → 重新解析重下（最多 3 轮、退避）；仍中招 → 任务失败，错误文案："上游返回广告占位音频，未入库，请稍后再试" |

- **期望时长**来自搜索结果（`Song.Duration`），随请求传递：`POST /api/online/download` 与
  `POST /api/online/preview` 新增可选字段 `duration`；`download_task` 新增 `duration` 列
  （迁移 `20261118090000_add_download_task_duration`）。旧客户端不传时，防线 1/2 的
  bitrate 异常 + 短片段兜底仍然生效；
- **试听**走同一套校验（`ResolveValidated`，重试 3 次），失败返回明确文案，WEB/APP 均会展示，
  不会再把广告当歌播出；
- 广告/占位响应**不再写入直链缓存**，避免重试反复命中同一垃圾 URL；
- WEB（`ui/src/online/OnlineSearchSection.jsx`）与 APP（`MusicRepository.kt`）请求体均已补 `duration`。

### 18.4 测试

- `server/online/validate_test.go`：bitrate=1 / 时长不符 / 短片段 / 正常曲放行 / 容差边界；

## 19. 迭代：上游拦截识别 + 提示分层 + 请求节奏（M5.5，2026-11-18）

### 19.1 背景：口令墙随时可能从「网页」挪到「接口」

上游站点网页端的下载入口由前端脚本拦截（点第 6 次下载弹出扫码口令页），正常情况下服务端
直接调 `POST /ajax.php` 完全碰不到这套逻辑。但它随时可能被搬到接口层，届时上游会返回
**HTML 口令页 / 网关拦截页 / 人机验证页 / 被截断的 JSON**。旧实现的唯一反应是
`json.Unmarshal` 抛出 `online/hicn: parse envelope: invalid character '<' …`：

- 运维看不出这是「上游换了规则」还是「我们自己解析写错了」；
- 任务失败文案把这种原文直接写进任务行，APP 普通用户也会看到；
- 每次失败都立刻重试，等于持续撞击上游风控，可能把临时拦截升级成封禁。

### 19.2 判定规则（先看内容，再看状态码）

判定只看**响应正文**，不信任 `Content-Type`（代理常改写头）：

| 正文特征 | 归类 | 说明 |
|----------|------|------|
| 去掉 BOM/空白后首字符为 `{` 或 `[` | **放行** | 按正常接口响应解析，正常 JSON 零误判 |
| 含「口令 / 解锁 / kl.php / 11.php / 请输入密码」 | `password-gate` | 上游把口令校验挪到了接口层 |
| 含「验证码 / 人机 / 风控 / 访问过于频繁 / 操作频繁 / captcha / cf-challenge」 | `anti-bot` | 风控/人机验证页 |
| 其它非 JSON（含空响应、网关错误页、改版页） | `non-json` | 统一兜底 |
| 正文是 JSON 但 `code != 0` 且 `msg` 命中上面两类关键词 | 同上两类 | 上游用信封报拦截 |
| 本站在冷却期内主动拒绝 | `cooldown` | 见 19.5，不发任何请求 |

`code != 0` 但 `msg` 无拦截特征时仍是普通业务错误（如 `code:-2` 参数校验失败），不当作拦截。

### 19.3 实现（服务端）

| 文件 | 改动 |
|------|------|
| `server/online/upstream_blocked.go`（新增） | 拦截领域模型：`ErrUpstreamBlocked`、`UpstreamBlockedError{Source,Action,Kind,Detail}`、四种 kind 常量、`classifyBlockedResponse`、`blockedKindFromText`、`snippet`（120 rune 截断 + 控制字符清洗）、`UpstreamBlockedHint`（运维文案）、`UpstreamBlockedNeutralText`（用户文案） |
| `server/online/hicn.go` | `postOnce` 先分类再判状态码：非 JSON 不再只报 parse 错；`429` → 记 30s 短冷却并视为可重试；`≥500` 可重试；拦截类错误不可重试并记 10min 冷却；冷却期内直接失败不发请求；重试退避时若正在限流冷却则先等冷却结束。新增 `cooldownUntil` / `setCooldown` / `cooldownRemaining` / `cooldownError` / `blocked` |
| `server/online/manager.go` | `taskErrorText(ctx, err)`：拦截类错误在**任务行**降级为「在线下载源暂时不可用，请稍后重试」并写 Warn 日志（含 kind/动作/正文片段），其它错误保留原文，排查能力不退化 |
| `server/nativeapi/online.go` | `writeSourceError(w, r, err, fallback)`：拦截类错误返回 `502` + JSON `{"error":…,"code":"UPSTREAM_BLOCKED","kind":…}`；是否返回运维文案由请求头 `X-Online-Client` 决定。`search`、`preview` 两个同步接口接入；下载失败写操作日志时用运维文案（操作日志仅管理员可见） |
| `ui/src/dataProvider/httpClient.js` | 管理端所有请求统一带 `X-Online-Client: web-admin` |
| `ui/src/online/OnlineSearchSection.jsx` | 搜索组失败时用 `errorText(e)` 取服务端 JSON 里的 `error` 字段，以 `Alert` 展示（原来只有一句 `Bad Gateway`） |

### 19.4 提示分层（关键约束）

| 调用方 | 标识 | 看到的内容 |
|--------|------|------------|
| 网页管理端（react-admin） | `X-Online-Client: web-admin` | 中文运维提示，按 kind 区分「上游要口令 / 被风控 / 冷却中 / 非接口内容」，并提示**持续出现需要更换下载源** |
| APP、第三方客户端、无标识调用 | 不带该头 | 仅「在线下载源暂时不可用，请稍后重试」 |

- 下载任务是异步的：任务行对所有用户可见，因此 `task.Error` 一律是中性文案；
  运维视角的细节放在**服务端日志**与**操作日志（仅管理员）**里；
- 任何一侧都不会把上游原始正文（含口令页 HTML）回给客户端；`error` 里只出现归类后的说明；
- APP 端无需改动（它本来就不发该头），WEB/APP 的失败表现因此自动分层。

### 19.5 请求节奏与冷却

| 参数 | 值 | 说明 |
|------|----|------|
| `minInterval`（基线间隔） | 2s | 全局串行，一个进程内同一时刻只发一个上游请求 |
| 抖动区间 | `[2s, 3.5s)` | `spread = minInterval/4*3 + 1`，让间隔不是固定节拍，降低「规律爬虫」特征（原实现是 `[2s, 3s)`） |
| 拦截冷却 | 10min | 命中口令/风控/非 JSON 后整个下载源静默，期间请求直接失败，不再触碰上游 |
| 限流冷却 | 30s | 上游显式 `429` 后短冷却，重试前先等冷却结束 |
| 直链缓存 | 1h | 未变（命中广告/占位音频时会主动失效，见第 18 节） |

- 不做口令自动绕过：那是主动对抗上游访问控制，且口令属于上游账号体系，不在本功能范围内。
