## 1. 结论摘要

1. **架构与基础设施层（重试/熔断/限速/缓存/分页/302 降级/转码/凭据安全）已实现且有单测**，
   上一版把这些判为"缺失"的 🔴 高风险不成立，不需要重复建设（清单见 §2）。
2. **真正的上线阻断项是 2 个 P0**（上一版均未发现）：
   - 有声书 `rescan`/`rescanAll` **先删章节再读目录**，网盘书点一次"重新扫描"即被清空；
   - `uploadCover`/`uploadNarratorAvatar` 无限制抓取用户输入 URL，存在 **SSRF**。
3. **上一版整改建议中有 3 条违反风控红线**（10 req/s 限速、整文件哈希去重、凭据入备份），
   必须否决（见 §5）。
4. **上线路径**：修完 P0（+P1 前 3 项）→ 进入 M6 NAS 端到端联调 → 联调通过后上线；
   P2 项迭代进行。修订后的验收清单见 §6。

### 3.1 关于问题 1（唯一标识）的准确表述

代码事实：

- `media_file` 行的自然键是 **`(path, library_id)`**（`persistence/mediafile_repository.go:174`
  `putByMatch(Eq{"path":..., "library_id":...})`）；`media_file.id` 是入库时生成的随机 ID
  （`persistence/sql_base_repository.go:645`），靠自然键匹配在重扫中保持稳定。
- `PID` 是**标签哈希**（`consts/consts.go:129` `DefaultTrackPID = musicbrainz_trackid|albumid,discnumber,tracknumber,title`），
  不是路径哈希。
- 因此**真实风险是**：网盘内文件**移动/重命名** → 行按路径匹配不上 → 旧 ID 失效 →
  歌单/进度/收藏引用断链。这与本地库是同一语义（Navidrome 存量行为），并非网盘引入，
  但网盘上改名更常见，值得缓解。
- **上一版的整改前提不成立**：OpenList `/api/fs/list` 的 `ObjResp` **没有稳定文件 ID**
  （官方结构：`name/size/is_dir/modified/created/sign/thumb/type/hashinfo`），
  仓库 `adapters/openlist/types.go` 的 `Entry` 据此建模。`source_file_id` 方案落地前
  必须先实测目标驱动是否返回稳定 ID（见 §5 待验证项）。

## 4. 上一版遗漏的真实问题（本次新增）

### 4.1 🔴 P0-1：有声书 `rescan` / `rescanAll` 对云库具有破坏性

**位置**：`server/nativeapi/audiobook.go`（`rescan` :587、`rescanAll` :668）

**现象**：执行顺序是 **先删章节、后读目录**：

```go
_ = repo.DeleteChapters(bookID)                    // :602 先删光章节
bookPath := filepath.Join(lib.Path, book.Path)     // :605
entries, readErr := os.ReadDir(bookPath)           // :606 云库上必失败
if readErr != nil { http.Error(w, "Cannot read directory: ...", 500); return }
```

对网盘库（`lib.Path = openlist://...`），`os.ReadDir` 必然失败 → 返回 500，
**但章节已被清空且不会回滚**。用户在网盘书上点一次"重新扫描"，这本书就空了。
`rescanAll`（:693/:697）同序同险。

**根因**：M5（设计文档 §7.5）改造了扫描/播放/封面链路，但**这几个后台管理接口漏改**，
仍直接读本地磁盘（`os.ReadDir` / `os.Stat` / `filepath.Join`）。

**修复方案**：

1. 走 storage 抽象：`storage.FSFor(ctx, lib.Path)` + `fs.ReadDir` / `fs.Stat` + `path.Join`
   （照抄 `scanner/audiobook_scanner.go` 的 `audiobookFS` 写法）；
2. **调整顺序**：先枚举出新章节列表成功后，再 `DeleteChapters` + 写入，保证"要么不改、要么改完"；
3. 失败时保留原章节并返回明确错误（区分"目录不可达"与"目录为空"）。

**验收**：网盘书执行 rescan 后章节不丢；本地库行为不变；补单测
（云库 rescan 成功 / 云库目录不可达时章节保留）。

### 4.2 🔴 P0-2：`uploadCover` / `uploadNarratorAvatar` 存在 SSRF

**位置**：`server/nativeapi/audiobook.go:779`、`:865`

```go
imageURL := r.FormValue("url")
client := &http.Client{Timeout: 30 * time.Second}
resp, err := client.Get(imageURL)   // 用户输入的任意 URL，无任何校验
```

任意登录用户可让服务端发起对任意目标的 GET：内网探测（`http://192.168.x.x`、
`http://169.254.169.254` 云元数据）、端口探测、绕过网络边界拉取内容。

**修复方案**：

1. 协议白名单：仅 `http`/`https`（拒绝 `file:`、`gopher:`、`ftp:` 等）；
2. 目标限制：解析后拒绝环回 / 链路本地 / 私网 / 组播地址（若确有内网图源需求，
   提供显式配置白名单 `CoverURLAllowHosts`，默认不允许）；
3. 加固：跟随重定向时逐跳复检、限制响应体大小（如 10MB）、保留 30s 超时；
4. 复用同一处校验工具，两处调用点（封面、头像）一并收敛。

**验收**：请求 `url=http://127.0.0.1:xxx`、`http://169.254.169.254/`、`file:///etc/passwd`
均被拒绝并记安全日志；正常公网图片上传不受影响。

### 4.3 🟡 P1-1：`rescan` 会清零章节时长、章节 ID 退化为文件名

**位置**：`server/nativeapi/audiobook.go:640`（`ID: af.name`）、`:647`（`Duration: 0`）、
`:726`、`:730`

重建章节时 `Duration` 写 0、`ID` 用文件名，覆盖既有记录后 **时长/总时长丢失**、
章节 ID 语义与 `scanner` 侧（`id.NewRandom()`）不一致。

**修复方案**：rescan 优先保留原章节的 `Duration`/`ID`（按 path 匹配），
新发现的章节走与扫描器一致的标签读取（storage + taglib，云库自动是 Range 懒读取）。

### 4.4 🟡 P1-2：长章节转码的直链过期断流（设计文档 §10.3② 遗留）

直链是**小时级有效**的签名 URL。转码模式把它当 ffmpeg 输入（`core/ffmpeg/ffmpeg.go:151`），
数小时长的有声书章节转码到中段可能因直链过期断流。

**修复方案**（设计文档已给）：改为把远端流灌给 ffmpeg stdin
（`core/ffmpeg.start` 已支持 `io.Reader`，改造面小），或转码前刷新直链 + 失败自动重试一次。
**注意**：有声书章节播放目前是 raw-only（设计文档 §10.3⑤ 有意为之），此项在启用
有声书转码前必须先落地。

### 4.5 🟡 P1-3：网盘后台接口与 storage 抽象的整体缺口

`rescan`/`rescanAll`/`uploadCover` 只是点位，建议**统一排查 `server/nativeapi` 中所有
`os.*`/`filepath.Join(lib.Path, ...)` 调用**并接入 storage 抽象；网盘库的写操作
（传封面）应明确语义：写回网盘不可行时，落到本地数据目录（如 `data/audiobook-covers/<id>`）
并在 `CoverPath` 上区分来源。

## 5. 否决项与红线对齐（重要）

以下上一版建议**不予采纳**，原因均为与设计文档 §4 / §15.1 冲突：

| 上一版建议 | 处置 | 理由 |
|---|---|---|
| 网盘 API 全局速率限制 **10 次/秒** | ❌ 否决 | 与 §4 风控设计（列表 ≤1 req/2s + ±20% 抖动）冲突。本项目核心约束是规避网盘风控（2026-06 起各网盘严打第三方工具），提高请求频率 = 提高封号风险。现有双令牌桶即为准 |
| 跨源去重用**文件哈希** | ❌ 否决 | 违反 §15.1「绝不为扫描整文件下载/算哈希」，几 TB 流量即风控事故。替代：OpenList `ObjResp.hashinfo` 元数据（部分驱动直给哈希，零下载）或 size+时长粗匹配，且以**提示**代替自动删除 |
| `backup` 打包**云源配置** | ❌ 否决（需脱敏版） | 凭据在 `navidrome.toml`/env，入备份归档 = 网盘凭据落盘外泄，违反「凭据不入库/不外泄」。可改为备份**非机密部分**（网关名/URL/远端路径），凭据由用户自行保管 |
| `source_type + source_file_id` 联合主键 | ⏸ 暂缓 | 前提"OpenList 返回稳定文件 ID"未验证（§3.1）。先做实测：对目标驱动抓 `/api/fs/list`，确认 ID 存在且改名/移动后稳定；成立再立项 |
| 新增数据库迁移脚本 | ❌ 无需 | 云源改造未新增列，不存在迁移风险 |

**待验证项（联调时做）**：OpenList 各驱动（阿里/夸克/115/百度）`/api/fs/list` 是否返回
稳定文件 ID、`hashinfo` 是否可用。结论回来后重评 §3.1 与 P2-8 的方案选型。

## 7. 附录：上一版事实错误清单

供评审流程留档，避免后续再被引用：

1. 「本地媒体以绝对路径作为唯一标识」→ 实为 `(path, library_id)` 自然键 + 随机 ID + 标签 PID；
2. 「无统一的重试、熔断、降级策略」→ `adapters/openlist` 三件套 + 播放三级降级均已实现并有单测；
3. 「网盘元数据无本地缓存」→ `DirCacheTTL` + DB 永久缓存已实现；
4. 「播放链路未明确服务端代理还是客户端直链」→ 设计文档 §0.4/§2 定稿 302 直链优先；
5. 「增量扫描依赖 mtime/size，网盘字段不一致会失效」→ 现为目录 hash（size+mtime），
   OpenList `modified` 为 RFC3339 稳定字段，风险为推测且影响可控（最坏是多读一次标签）；
6. 「路径遍历漏洞」→ `fs.ValidPath` + `os.DirFS` 语义已阻断 `../` 与绝对路径；
7. 「SSRF 在代理拉取链路」→ 302/中转的 `raw_url` 来自网关非用户输入；真实 SSRF 在 `uploadCover`；
8. 「凭据可能在日志/错误信息明文输出」→ 全仓核查无凭据/签名 URL 日志，`RedirectDirect` 不写响应体；
9. 「当前仅支持手动全量扫描」→ `Scanner.Schedule` cron + `ScanOnStartup` 已覆盖；
10. 「`dedupe` 无 `--dry-run`」→ `cmd/dedupe.go:16-19` 已有；
11. 「`scanner/genre.go` 分类识别」→ 文件不存在，实为 `core/library.go:63 detectMediaType`；
12. 「播放进度、书签、歌单、收藏均按文件路径关联」→ 均按 ID 关联；
13. 「网盘文件流未接入转码管线」→ 已接入（直链作 ffmpeg 输入）且有转码缓存；
14. 「新增云源字段后无迁移脚本，升级会损坏」→ 未新增列，迁移框架（125 个）本就存在；
15. 「异常场景（超时/鉴权失败等）未覆盖」→ `openlist_test.go` 已含 401 重登、429/5xx 退避、
    熔断开合、节流抖动、读取预算等用例。
